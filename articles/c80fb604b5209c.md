## 作ったもの

テックブログの記事につけるOG画像（1200×630のアイキャッチ）を作るWebアプリケーションです。ブラウザ上の`<canvas>`で作成する方法と、`/api/og`というエンドポイントのAPIを使ってサーバーサイドで作る2つの機能を提供します。

また、SlackやXなどでの画像展開は拡張子でファイルフォーマットを判定することがあります。そのため貼り付け用には、`.png`で終わる`/og.png`を用意しました。実体は`/api/og`へのrewriteです。

## 最初はブラウザで完結する単一HTMLとJavaScriptだった

もともとは1枚のHTMLファイルに全部詰め込んだツールでした。フォームに入力すると`<canvas>`に描画され、`toBlob()`でPNGを書き出して手元に保存する、サーバーを一切介さないツールです。

これを[ロリポップ！デプロイナウ](https://lolipop.jp/deploy-now/)で動かすためにNext.jsに移植する過程で、生のNode.jsが動くと気づきました。サーバー側でも同じ画像を生成できれば、URLひとつでOGP画像が作れると思い、せっかくなのでAPIも追加することにしました。

## 描画コードをブラウザとサーバーで共有する

ポイントは、canvasへの描画コードを1箇所にまとめて、ブラウザとサーバーの両方から呼ぶことです。これをやらないと、フォームのプレビューと実際に配られるOG画像が微妙にズレるという事故が起きます。

```
app/scene.ts             ← 描画の本体（ここだけ）
app/OgImageGenerator.tsx ← ブラウザ側: <canvas>にscene.tsを流す
app/api/og/route.ts      ← サーバー側: @napi-rs/canvasにscene.tsを流す
```

`scene.ts`は`createScene(state, images, createCanvas)`という関数で、`document`や`window`には一切触れません。canvasの生成だけを外から関数として受け取る形にして、DOM依存を切り離しています。

```ts
export type CanvasFactory = (w: number, h: number) => HTMLCanvasElement;
```

ブラウザ側はそのまま`document.createElement('canvas')`を渡し、サーバー側は`@napi-rs/canvas`の`createCanvas()`を渡します。`@napi-rs/canvas`は、ブラウザのCanvas 2D APIとほぼ同じインターフェースを実装しているネイティブモジュールです。そのため`ctx.fillText()`や`ctx.drawImage()`といったメソッドも同じコードで動きます。型だけDOMのものに寄せてキャストしています。

```ts
// app/api/og/route.ts
const canvasFactory: CanvasFactory = (w, h) => createCanvas(w, h) as unknown as HTMLCanvasElement;
```

## サーバーサイドAPIでハマったところ

Node.jsが生で動くとはいえ、サーバーサイドでcanvasを描くのはブラウザとは別の面倒さがあります。

### ネイティブモジュールはバンドルさせない

`@napi-rs/canvas`はプラットフォームごとのバイナリを持つネイティブモジュールなので、Next.jsのバンドル対象から外して実行時に`require`させる必要があります。

```ts
// next.config.ts
serverExternalPackages: ["@napi-rs/canvas"],
```

### `fs`で読むファイルは追跡されない

`/api/og`はフォントファイルと背景画像を`fs.readFile`で直接読んでいます。`standalone`出力はコード解析で使われているファイルを自動的に集めてくれますが、`fs`越しのアクセスまでは追いかけてくれません。書き忘れるとローカルでは動くがデプロイした先ではエラーになってしまいます。

```ts
// next.config.ts
outputFileTracingIncludes: {
  "/api/og": ["./fonts/*.otf", "./public/bg/*.png", "./public/logo-default.png"],
},
```

### 可変フォントは使えない

サーバー側のレンダリングエンジン（skia）は可変フォントの`wght`軸を解釈せず、太さ指定がすべて同じウェイトに潰れます。そのためRegular・Medium・Boldの静的ウェイトOTFを3本個別に登録しています。ブラウザ側は素直にGoogle Fontsの可変フォントを使えるので、ここはサーバー側だけの制約です。

### 任意の画像URLは受け取らない

これはハマりどころというより設計判断です。`/api/og`に画像URLを渡せるパラメータは作りませんでした。サーバーが任意の宛先へアクセスできてしまう、いわゆるSSRFの原因になるためです。画像はGravatarと`public/`配下の固定素材だけに絞っています。フォーム側もファイルアップロードの口を持たないので丸ごとクエリパラメータとして表現できます。その結果、フォームで作った画像とURLから生成した画像が常に一致するという性質も得られました。(フォントを除く)

## ロリポップ！デプロイナウへのデプロイ

```bash
npx lolipop deploy
```

これだけです。`.lolipop/project.json`でプロジェクトと紐付いていれば引数なしで通り、ビルドはサーバー側で走ります。キューに入ってから公開まで3分ほどでした。

また、AIエージェントを使って開発をしていれば「https://deploy.lolipop.jp/skills/lolipop-cli.md を読んで、公開までの手順を進めてください。」を指示するだけでデプロイできます。( https://lolipop.jp/deploy-now/ で公開されているプロンプトです)


## まとめ

- OG画像ジェネレーターを、ブラウザ完結の単一HTMLからNext.jsに移植した
- 移植のついでに、描画コードを`scene.ts`に切り出してブラウザ・サーバー両方から共有する構成にした
- ロリポップ！デプロイナウはNode.jsアプリをそのまま動かせるので、フォームだけでなく`/api/og`というサーバーサイドAPIも追加できた
